## Concrete profile choices

The first installation profile targets the standard nested `unknown-knowledge`
seeded layout. The existing finite root-layout migration remains available; custom
or root-level installation activation is not inferred from a default seed profile.
Private installation input is `{version:1,roles,launches,limits}`. Each role is
`{file,role,disposition,reason,edits,bindings}`; a reference edit is the exact
`{start,end,expected,source}` span. Those edits and source keys remain private.
Suppression bindings distinguish each exact row's literal keys from its typed
stale-concept identity pair. The safe inventory retains file captures and role
judgments, not reference correspondence. Final verification requires separately
supplied trusted `approvedInstallationReview`, using the existing orchestration
review boundary. Its digest binds source, candidate and the derived inventory;
neither caller hashing nor the report predicate authenticates approval.

The actual audit owners count surveyed kit files even though they skip those
files when building effective findings. Replacing a distribution can therefore
change the raw candidate count. Retain each actual count, corroborate it against
that owner's actual survey, and compare the complete effective candidate sequence
outside the fixed kit prefix, scope, unsurveyed disclosures, actual findings and
warnings. No user-source count difference is waived. The only other audited
non-ID change is the exact known vendor draft prompt: numeric range allocation
becomes qualified proposal authoring. Original raw output remains separate.

The complete expected tree includes exact deletion entries. Shared attribution
also names unchanged copy sources; installation comparison removes only those
whose before/after blob and mode are actually equal. This preserves both full-tree
equality and exact changed-path equality during runtime replacement.

## Seeded assets and wrapper treatment

The fixed profile includes the unconditional manifest-selected protocol, hooks,
templates, adapter fixture pairs and seeded documentation. Historical bytes and
their original source paths are frozen in `engine/policies/installation-assets.json`
at `08066b5f527b9d7d9705a3367bc26dcf080271ad`. Current assets come from the
trusted distribution and are captured with the migration runtime. Optional stack
fixture packs and customized vendor assets are unsupported by this first profile.
An unknown or changed vendor file causes refusal; the profile never replaces a
custom file merely because its path resembles a vendor path.

The `seeded-wrapper` role accepts the actual historical platform templates and
replaces only the generated body. Shared Codex/Copilot sections require exactly
one well-formed sentinel pair and preserve all bytes outside it. Dedicated
Claude/Gemini/Cursor files must match the historical generated file exactly.
Skipped, malformed or customized wrappers need a separately supported reviewed
treatment. This profile never assumes a platform loaded a pointer just because
the file exists.

## Observed local activation

`verifyMigrationActivation` is an internal read-only API. Its input carries the
same retained validation/review bundle digests, private migration resupply and
trusted runtime/installation review used by publication, plus explicit observation
limits (`maxFiles`, `maxBytes`, `maxOutputBytes`, `maxCommandMilliseconds`). The
trusted installation review additionally binds:

```json
{
  "activation": {
    "hooksPath": ".hooks",
    "externalConsumers": "none",
    "environment": "current-process"
  }
}
```

This is an independently reviewed scope judgment, not an engine discovery result.
Unknown required external consumers block review. No separate approval mechanism
is introduced. The supported executable hook is the literal `shell-node` form:

```sh
#!/bin/sh
exec node unknown-knowledge/engine/commit-check.js --root .
```

The reviewed repository-relative hooks directory must contain only this
executable `pre-commit` launcher. Merely seeding the vendor hooks does not activate
them. Dynamic shell scripts, external hook directories and environment location
overrides are unsupported. The current-process PATH must resolve the same Node
executable captured in validation; Node module/option and dynamic loader overrides
refuse. Index entries and every live repository file outside `.git` must match
the candidate captures, so an unknown untracked reader also blocks observation.
The verifier checks HEAD and the published output ref and observes local state
both before and after fresh final verification. It never executes a discovered
script, performs a checkout, updates a ref or edits Git configuration.

A successful result is `observed` with scope `bounded-local-installation` and
`futureState: not-guaranteed`. It records local state during this check; it does
not atomically deploy files or switch running processes, CI services or IDEs.
Publication alone remains `activation: not-observed`. Failed observation leaves
the candidate ref intact. Before publication a candidate can be discarded; after
publication, repairs move forward with the allocated identities and never restore
legacy readers against canonical data or retain an old-ID lookup table.

## Limits and integration documentation coverage

Class/range retirement currently admits block-style `id-range: [K-100, K-199]`
lines only. Unknown rule fields, unsupported layouts, customized vendor assets
and malformed suppression syntax refuse. Malformed individual suppression rows
can remain as explicitly literal rows: actual native audit evidence must retain
their fail-open warnings. A row needed simultaneously as a literal key and a
stale-concept identity has no combined disposition; resolve that ambiguity under
review before migration. Unknown or unresolved exact record references retain
the existing inventory/adjudication refusals. There is no numeric normalization.

The local activation profile admits only the literal executable pre-commit hook
and static committed launch bindings. It does not verify an IDE's loaded state,
an npm process, a remote runner, shell aliases or future environment changes.
All nonempty `GIT_*` variables are unsupported in the observing process, including
otherwise benign host-injected settings; use an explicit supported environment.
The complete live-tree check also requires retained evidence to reside outside
the observed repository. Capacities bound admitted files/bytes/outputs and command
time; they are not a whole-host memory or filesystem-I/O guarantee.

Scoped guides updated together: prepared migration, final migration, source
profiles, historical runtime, candidate review, final publication and this guide.
The current seed manifest already includes `engine/`, so the new modules/policies
need no manifest entry. No public CLI flags, persisted store schemas, default
seed behavior, wrapper template, protocol conduct or contributor workflow changes.
Tests exercise preserved historical assets without rewriting their provenance.
Root README/AGENTS, package version, both root lockfile version fields, changelog
and shared acceptance/contributor/migration coverage belong to the integration
owner's single PR; this worker commit is not a separate PR or publication.

## Loader-environment follow-up

Independent review found that the initial selected-variable check omitted Linux
`LD_AUDIT`. That source-confirmed gap could pass a loader override to the first
Git spawn; no DSO payload was executed or reproduced. The finite local profile
now rejects every nonempty `LD_*` and `DYLD_*` variable before any child spawn,
alongside the existing `GIT_*` family and explicit Node/location overrides.
Empty values remain absent overrides. This is a correction to the existing
restricted environment boundary, not support for additional launch forms.

The actual retained-review/publication vertical includes `LD_AUDIT` and
`DYLD_FRAMEWORK_PATH` regressions. Each installs spies for both child-process
spawn APIs before injecting a host-safe sentinel, then requires the ordinary
`activation-environment-unsupported` refusal and zero spawn attempts. The spies
never delegate, even on RED, and restore the environment and built-in exports
before the positive activation check. Positive fixture cleanup covers the same
complete environment families. Original frozen receipts above remain unchanged;
the focused follow-up receipts accompany the corrective patch.

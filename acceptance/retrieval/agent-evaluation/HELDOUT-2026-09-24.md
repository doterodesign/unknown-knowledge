# Held-out agent comparison, 2026-09-24

The first agent evaluation with `ask`. Same six held-out cases, same reader
model, same content; only the runtime differs. Per-session rows are in
[heldout-2026-09-24.json](heldout-2026-09-24.json).

## Result

| | Original runtime (08066b5) | Current runtime (rc.19) |
| --- | --- | --- |
| Cases the reader completed or correctly declined | 4 of 6 | 4 of 6 |
| Of the 4 cases that ran | 4 of 4 | 4 of 4 |
| Blocked by the API before an answer | 2 | 2 |
| Critical errors | 0 | 0 |
| Reader cost, all 6 sessions | $1.41 | $1.43 |

Every case had the same verdict under both runtimes: 4 ties and 2 blocked,
with no regression and no improvement. The two answerable cases that ran were
completed, and the two scoped negatives that ran were correctly declined.

On the four cases that ran, the current runtime's reader made 10 to 22 tool
calls (the original's made 10 to 19) and received 49 to 63 KB of tool output
(the original's 44 to 49 KB) in total across the session.

**Blocked sessions.** For two cases, manufacturing-01 and holding-company-01,
the API refused the reader session in both runtimes under its usage policy (a
`[bio]` classifier tag) and no answer was produced. That is the model
provider's classifier firing on the case content, not a runtime result. The
sessions count as failures as the protocol requires; they were not retried,
replaced or rerouted to another model.

## Method

- **Cases.** Six new cases, one per development-v2 organization, three
  answerable and three scoped negatives. An independent custodian agent wrote
  them and a separate reviewer agent checked entailment and novelty against
  the 54 existing questions; 3 were accepted and 3 revised. They are sealed
  outside the repository; this repository holds only the
  [blinded receipt](../../../docs/agents/2026-09-24-heldout-custody-receipt.md).
  The engine's tuner never saw them. These are new cases: the result cannot be
  compared one to one with the earlier 15/18 vs 10/18 study, whose sealed cases
  no longer exist.
- **Content.** The eight development-v2 installations built as 2.x stores by
  the 08066b5 runtime (`materialize-corpus.js`), and the same stores converted
  by `migrate.js` into a fresh 3.0 kit (`arms.js`). Subjects are not part of
  either, so `ask` ran without Subject labels.
- **Readers.** One headless Claude Code session per case and runtime, Sonnet 5,
  isolated as described in the [retrieval README](../README.md#agent-evaluation),
  with a $2 budget per session. Model chosen on the public pilot tasks.
- **Grading.** `grade.js` with Sonnet 5, rubric fixed before these sessions
  ran. Only verdict codes and critical flags left the custody directory.

## Limits

- One repeat per runtime, so a single lucky or unlucky session moves a case.
- Four usable cases. A tie on four cases shows no regression on these cases.
  It does not show that `ask` improves agent task completion.
- All grades come from one grader model; case judgments come from one
  custodian and one reviewer, both agents.
- One case's key evidence partly overlaps records used by an existing
  development question (the reviewer could not avoid it in that organization).

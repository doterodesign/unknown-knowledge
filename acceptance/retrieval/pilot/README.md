# Six-task development source pilot

`tasks.json` describes six distinct development cases and their source records.
`judgments.json` records source-based expected candidates and independently
reviewed relevance/response judgments. `manifest.json` pins their exact bytes.
The public sources are synthetic; no claim about real companies or research
is asserted. See `REVIEW.md` for review provenance and corrections.

This is a frozen **source/task/rubric pilot**, not six executable installations
or a complete benchmark. No trial, runtime result, latency, memory target or
retrieval improvement has been recorded. The target registry/query versions
and operational budgets are deliberately unset. Set them after actual pilot
baseline measurement, before comparative runs or ranking optimization.

## Reading the data

Each source passage is independently addressable by `sources/<file>.md#heading`.
Record IDs are test-ledger qualified identities with namespace/kind/exact ID;
these JSON rows are not production RecordRef objects or loadable store records.
`subjectKeys` are symbolic keys in the declared forest, not authored S IDs or
an approved subject registry. Absent `subjectKeys` means unknown classification;
`[]` means a known recorded empty set. Related pairs represent association,
never membership or ancestry. Lifecycle labels describe fixture intent and
must be explicitly mapped to each store's schema when installations are built.

The source-only `scope` annotation is not a new engine predicate. An empty
legacy scope list, an unknown/null scope and an explicitly unrestricted new
scope must remain distinct during materialization; never turn a reviewer's
applicability judgment into authored scope or approval metadata.

Candidate expectations apply only to the explicit declarative `candidateRule`.
They remain separate from relevance, applicability, source review and response
adequacy. These are all-view direct-subject predicates; the holding request
requires a typed capability refusal, not successful empty candidates. None
claims an encoded/validated P4 query or a P5 semantic-completeness verdict.

`grade` measures usefulness to the scoped task response. `applicable` means an
allowed contribution to that response, **not** engine eligibility, freshness,
human approval or authority for every claim. The `reason` states each limit:
the controller's grade 1 helps distinguish a maximum from a setpoint but cannot
answer a site's setting; a predecessor helps explain a conflict but is not
current authority. Grades 2–3 count toward applicable recall only for tasks
where that metric is defined.

`answerable: false` for services and holding means the requested approved fact
or combined operation is unavailable. Both still have useful explanation
evidence. Their rank/factual-bundle metric values remain undefined; raw
relevance counts are diagnostic only and must not enter aggregate recall.
`abstentionTarget`, `outcomeRequired` and `explanationBundles` specify the
separate response review. Policy is answerable because its prompt explicitly
requests an explanation when a unique authority is not established; choosing
one period is still forbidden. A source hit never proves actual agent conduct.

## Trial preparation still required

Materialize one isolated fixture root per task/condition with the real baseline
runtime, store catalogs/rules, source paths and confirmed source scope. Use the
existing initializer/fixture conventions and review the installed records
against these sources. Pin old and target fixture versions separately; do not
introduce a retained old-to-new lookup table. Baseline interpretation uses the
actual original CLI plus documented catalog/source recovery. New structured
plans require the released domain interfaces; this pilot adds none.

Keep the evaluator's judgments and other organizations' sources out of trial
context. Services explicitly excludes `sources/private/`; do not supply that
draft to its retrieval agent. A subjectless engineering variant must keep
supported baseline lookup usable while reporting subject operations unavailable.
Policy's primary installation contains Decisions only. Holding consists of
three disconnected namespaces and must never be presented as one loaded union.

One Markdown document currently contains all public passages for each case.
An agent can inspect that whole document cheaply. The baseline must therefore
record both document-read and passage/record inspection costs and equalize
source access between conditions; top-10 presence alone is not an efficiency
gain. Operational budgets will be frozen after this measurement.

## Limits

These six tasks exercise one behavior family each. They do not supply the
final six-by-twelve suite, 24 held-out cases or a generalization result. Early
source drafts contained explicit rubric coaching; the reviewed versions remove
those instructions and retain ordinary source facts/limits. Some task wording
still gives explicit constraints, so these remain guided development cases.
Rouge aliases exist in the corpus but no task uses that alias. Non-ASCII input,
unrelated-section conjunction, fresh successor checks, stale/inaccessible
citations and the full authored-scope matrix require their own actual cases.
No test passes merely because this metadata exists.
